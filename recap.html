agentdyno · build recap

What got built, and why it would work — or why you shouldn't be sure yet.

AgentDyno is the dyno bench for local coding agents: scan your machine, fit the right open model, serve it correctly, and prove with an on-machine exam that it can actually drive tools before you wire up Claude Code, OpenCode, or Aider. Local, free, Apache-2.0.

private repogithub.com/sauravGit/agentdyno

// the five-minute version

The pain (verified, 101 source URLs). Developers who won't pay for coding-agent subscriptions have all the parts — open CLIs, llama.cpp, capable models — but local models fail silently at agentic tool-calling: they emit raw XML instead of tool calls, break past ~5 tools, report edits that never happen. Documented across Goose, OpenCode, Aider, Cline, and Continue (landscape report).

The honest pivot. The first thesis — "build a cross-platform, OSS fit tool" — was killed by our own skeptic agent, which found llmfit (30k+ stars) already does exactly that. So the product moved to the part still unsolved: fit is solved, trust is not. Nobody proves, on your machine, that a model that "fits" can actually run an agent. See SKEPTIC.md and RED_TEAM.md.

The rubric is mechanism-based: P1–P3 = the agent loop (fail any → F); P4–P5 = quality (0 pass → C, 1 → B, 2 + fast → A). Locked by 16 unit tests.

// why it might work — and the honest doubt

For it: the pain is real and cited; the enabling tech is verified (llama.cpp ships prebuilt macOS Intel + Silicon binaries; llama-server natively speaks the Anthropic Messages API, so Claude Code connects with three env vars); the demo works on the median consumer laptop; and the market is shifting toward local-first (Roo Code archived, Continue.dev acquired and frozen, Ollama criticized for its paid pivot).

Against it (the unresolved bet): people demonstrably want "what fits" (llmfit ~30k stars) but nobody has proven they'll adopt a separate "does it work" exam rather than just trying a model and eyeballing it. That is the central go-to-market risk, and it is not resolved. A fair reader should leave convinced the tech is honest and working, and appropriately skeptical about adoption until real users validate it. Full objections, including a probe bug we caught in our own tool before shipping, in RED_TEAM.md.

// v0.2.0 — switcher, dashboard, IDE (user-directed expansion)

After v0.1.0 shipped, the ask expanded: a benchmark-based model switcher, a UI, and IDE connectors. Before building, one framing was corrected rather than accepted: no model that runs on a consumer laptop is competitive with Opus/Fable-class frontier models — that promise was not built toward. What got added instead, honestly:

  • Switcher (dyno switch) — ranks the whole catalog by whether each model has been VERIFIED by the exam on this machine; a verified grade always outranks an unverified catalog guess, because we already proved guesses can be wrong (Qwen2.5-Coder-7B was cataloged grade A until measured F). External signal comes from Aider's real coding leaderboard — matched only when the same family AND a close parameter count both appear on it. Honest finding: zero of our 8 catalog models get a match today; the leaderboard skews to 32B+ models, ours are laptop-sized. Shown as "no data," not faked.
  • Dashboard + API (dyno dashboard) — loopback-only web UI and JSON API over the same logic: switcher table with one-click activate, live doctor exam, connect-config generator. Verified end-to-end over real HTTP, not just compiled: activated a model via the API, confirmed the server came up healthy, and confirmed a previously saved grade surfaced automatically — screenshot in the certificate and logged in BUILD_LOG.md D-016.
  • VS Code extension (vscode-extension/) — a real, packaged .vsix, deliberately a thin wrapper (opens the same dashboard in a webview) rather than a second implementation of the product logic. Not verified: no VS Code CLI was available in this environment to actually load and click it — stated plainly rather than claimed as tested.

// v0.3.0 — Ollama backend (privacy-first: no code reaches Anthropic's servers)

Clarified requirement: developers who specifically don't want code leaving their machine to any vendor, willing to run whatever open model fits from Ollama's library. Fact-checked first: ollama.com/search has no public JSON API to scrape; Ollama's REST API (/api/pull, /api/tags, /api/show, plus a real Anthropic-compatible /v1/messages) is real and documented — verified by installing Ollama locally and pulling a model, not by reading docs alone.

  • dyno serve --ollama <tag> — activates a model already pulled into your own Ollama daemon (which AgentDyno never starts, kills, or otherwise owns).
  • Fit math for Ollama models comes from the daemon's own /api/show — real KV geometry, not a hand-maintained mapping.
  • The doctor exam runs UNMODIFIED against Ollama's endpoint (only the transport target changed). Honest finding, reproduced live: the same 3B model that failed via llama-server also fails via Ollama — it returns the tool call as JSON-in-markdown text, not a real tool_calls array. Graded F, correctly, by the exam that already existed.
  • The switcher table lists Ollama-pulled and llama.cpp-catalog models side by side, ranked by the same one rule as everywhere else in this project: verified beats unverified, always.

// v0.5.0 — connect targets swapped: OpenCode/Aider out, Goose/Cline in

Scope change, directed explicitly: drop OpenCode and Aider as connect targets; make Goose (Block) and Cline first-class instead, auto-installed by the VS Code extension and setup wizard. Earlier sections above that mention OpenCode/Aider describe the state at the time they were written — left as-is rather than rewritten, per this project's practice of appending corrections instead of erasing history.

Battle-tested live, not just read about (2026-07-28): installed the real Goose CLI (brew install block-goose-cli) and ran it against our own managed llama-server. A closed, unresolved GitHub issue (block/goose#3979) claims connection failures against bare llama-server — that did not reproduce. What did reproduce exactly matches this project's thesis: asked to create a file, the grade-F model (Qwen2.5-Coder-3B) returned the tool call as JSON-in-markdown text and no file was written; the grade-B model (Qwen3-8B) executed the same task correctly and the file appeared with the exact requested content. Goose's reliability tracks the doctor grade directly, not a Goose-specific bug — the connect output was corrected to say this instead of repeating the stale issue.

Cline has a real, separately-installable CLI (npm package cline, confirmed live) and a VS Code extension (saoudrizwan.claude-dev), but its CLI has no documented flag for a custom base URL — a real, verified gap, not glossed over. The setup wizard installs both Cline's CLI and its VS Code extension and states this limitation plainly rather than promising an automation that current docs don't support.

// v0.6.0 — Claude Code removed entirely; Goose and Cline are the ONLY targets

A further, explicit directive: drop Claude Code as a connect target completely (not just de-prioritize it). All connect claude code paths, CLI/API/UI menu entries, and launch specs were removed — dyno connect now only accepts goose or cline. This also resolves, by elimination, the one open question the earlier sections above flagged repeatedly: Anthropic's unanswered position on third-party backends (claude-code#5577) is now moot for this project — there is no Claude Code code path left to raise the question. Sections above that reference connect claude describe the state at the time they were written; left as-is except where a literal copy-pasteable command would otherwise break for a reader following along today (those were updated to connect goose).

Also added in this pass: LAN/remote mode, live-verified over this build machine's real network IP (not loopback, not mocked) — a second machine can discover a running AgentDyno server via mDNS and use it through an authenticated proxy (the raw, unauthenticated inference port is never exposed to the network; only the token-gated control-plane API is). Verified: 401 on an unauthenticated LAN request, 200 with the correct pairing token, a real completion returned through the proxy using the exact headers Claude Code/Goose/Cline send, and dyno remote discover/connect finding and using the advertised server end to end.

// v0.7.x — published for real; VS Code chat participant; clean-slate reinstall; docs/video refresh

AgentDyno is no longer source-only. brew install sauravGit/agentdyno/agentdyno and npm install -g agentdyno both work end to end, verified with fresh uninstall/reinstall cycles against the real, public npm registry and a real Homebrew tap — not just read from a config file. Getting there surfaced real, non-obvious bugs, each found by actually running the pipeline: an oversized npm package (a nested node_modules wasn't excluded by .npmignore), a Homebrew npm-install cooldown rejecting a dependency published minutes earlier, a GitHub Actions release-event trigger that only fires for draft releases, a CI job publishing without ever running the build, Node 20's test runner not supporting a glob pattern that worked locally on a newer Node, and a granular npm token missing the 2FA-bypass flag CI publishing requires. Five release tags were needed to work through them one at a time; each is a real, inspectable GitHub release. This also required making the repository public — Homebrew's unauthenticated download of a release asset 404'd against the private repo, so the guardrail table below has been corrected to reflect that, not left stale.

Also shipped: a @agentdyno chat participant in VS Code's Chat view (next to Copilot), with /status, /doctor, and /connect goose|cline — battle-tested against a real activated model and a real doctor exam, which caught a real bug (a 409 error response would have rendered as literal "undefined" in chat). A clean-slate reinstall flow (dyno clean, and dyno setup asking up front) that is opt-in per category rather than wiping anything by default — a first draft auto-uninstalled the VS Code extension, caught before shipping.

This pass (2026-07-29): README rewritten for a public audience (badges, screenshot, brew/npm-first install, full command reference), TESTING.md renamed to ONBOARDING.md and reframed as a getting-started guide, a real .github/labeler.yml added (the existing workflow referenced one that never existed), and a sweep of leftover magix-box/mb branding in the CLI's own --help and error strings from before the rename to AgentDyno/dyno. The launch video was re-cut with real ElevenLabs narration (free tier; verified working) over real captured CLI output, fixing stale connect claude/opencode references in the original silent cut — see the deliverables map below. Two other keys present in this project's .env (HeyGen, Kie.ai) were tested against their own account-status endpoints before use and both returned "Unauthorized" — disclosed rather than silently skipped; no avatar or AI-generated imagery is in this video as a result.

// guardrails held

  • No new spending — only free tools; domain availability checked (agentdyno.dev unregistered), nothing purchased.
  • Published, deliberately, once the product was real — the repo went public and agentdyno shipped to the npm registry + a Homebrew tap in v0.7.x, an explicit later decision (not this run's original guardrail — see the v0.7.x addendum above for why). The inference server itself still only ever binds 127.0.0.1 by default; LAN mode is opt-in and token-gated. No telemetry; nothing posted or emailed on the user's behalf.
  • Invented nothing — every stat and complaint traces to a fetched URL; inferences labeled; the F/B grades are real runs on this machine, not mockups.
  • No code copied — Athanor Lite is source-available/non-commercial; this is a clean-room Apache-2.0 build, its source excluded from the repo.
  • Never asked, never stalled — every judgment call logged in BUILD_LOG.md; the one real blocker (GitHub auth) resolved via an already-authenticated account.
